# 9 · Architecture (שקף 10) ⭐

**WHAT I DO ON SCREEN:** **לא לעבור תיבה-תיבה.** לעקוב עם היד אחרי מסלול של הבקשה שהם בדיוק ראו — ה-upload.

# 10 · Agent & Sub-Agent (שקף 11) ⭐⭐

**TIME:** 1:15 · *החלק הכי מעניין — לאט ובביטחון*

**WHAT I DO ON SCREEN:** שקף 11 (Request flow). לעקוב עם היד: **Tutor Agent → Sub-Agent → MCP → Database**. לעצור על החץ בין ה-Agents.

**WHAT I SAY:**

> ועכשיו החלק שהכי מעניין אותי בפרויקט.
>
> ה-**Tutor Agent** מקבל משימה — והוא לא מבצע אותה לבד. הוא משתמש ב-**LangGraph**: LangGraph מתאר את ה-flow כ-**graph** של **nodes**, עם **state** שעובר ביניהם, וכל node מחליט מה השלב הבא. זה נותן לי flow **צפוי**, שאפשר לעקוב אחריו ולעשות לו **debug** — במקום prompt ענק אחד שעושה הכל.
>
> וכשצריך משימה מתמחה — הוא פונה ל-**Sub-Agent**. **Card Creator** כותב את השאלות מהחומר — זה מה שרץ כשהעליתי את ה-PDF. **Card Grader** מקבל את התשובה שלי, נותן score ומסביר מה היה חסר — זה מה שרץ כשעניתי.
>
> **וזו בדיוק communication between Agents** — Agent אחד מפעיל Agent אחר, מעביר לו רק את מה שהוא צריך, ומקבל תוצאה מובנית בחזרה.
>
> **ולמה בכלל Sub-Agent?** שלוש סיבות. **התמחות** — לכתוב שאלה טובה זו משימה אחרת לגמרי מלדרג תשובה, ולכל אחד יש prompt משלו. **context קטן ונקי** — כל אחד מקבל רק את מה שרלוונטי לו, וזה גם יותר מדויק וגם יותר זול. ו**תחזוקה** — אני יכולה לשפר את ה-Grader בלי לגעת ב-Creator.
>
> ואיך ה-Agent נוגע במידע? **דרך MCP.**
>
> ה-**MCP** נותן ל-Agent **tools**. וזו הנקודה: **ה-Agent לא ניגש ל-DynamoDB ולא ל-S3 בכלל.** ה-LLM יודע לעשות reasoning — הוא לא אמור לכתוב ל-**database**.
>
> אז כתבתי **MCP Server** משלי, עם tools כמו: ליצור deck, להוסיף card, לשלוף את מה שהגיע זמנו, ולשמור score.
>
> ה-Agent רק **מחליט** איזה tool הוא צריך — וה-**tool** מבצע. ככה ה-Agent לא צריך לדעת איך ה-database בנוי; הוא מקבל **interface** יציב במקום גישה ישירה.

**TRANSITION:** `↓` → שקף 12.

# ❓ שאלות צפויות

- **למה Sub-Agents ולא prompt אחד?** → התמחות, context קטן יותר, תחזוקה נפרדת.
- **למה MCP ולא לקרוא ל-database מהקוד?** → ה-Agent מקבל interface של tools, לא גישה ישירה ל-storage. ה-LLM מחליט, ה-tool מבצע.
- **למה S3 וגם DynamoDB?** → S3 לקבצים גולמיים, DynamoDB ל-structured data עם lookup לפי key.
- **מה אם ה-LLM מחזיר score לא תקין?** → נופל ל-"incorrect", ה-card חוזר מחר. ה-scheduling לא תלוי בפורמט של ה-model.
- **הכפתור `+1 day` לא מזייף את הדמו?** → לא. הוא מזיז **רק את התאריך** של המערכת. ה-intervals חושבו ונשמרו ב-DynamoDB לפני כן, בזמן אמת.
- **למה LangGraph ולא agent loop רגיל?** → flow צפוי שאפשר לעקוב אחריו ולעשות לו debug, עם state מפורש בין nodes.
