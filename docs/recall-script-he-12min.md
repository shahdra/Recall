# 7 · How It Works — 0:45

**על המסך:** שקף How it works / הזרימה.

> אז מה ראינו בעצם? שני flows.
>
> ה-flow הראשון — **ingestion**. אני מעלה **PDF**. הקובץ הגולמי נשמר ב-**S3**, הטקסט מגיע ל-**Agent**, וה-Agent מייצר ממנו cards. ה-cards נשמרים ב-**DynamoDB** ומקבלים מיד **due date** — הם חדשים, אז הם זמינים ללמידה עכשיו.
>
> ה-flow השני — **study**. אני מבקשת את מה שהגיע זמנו היום, עונה, וה-Agent מעריך את התשובה. וכאן קורות שלוש פעולות: הוא מייצר **feedback**, הוא מחשב **מתי ה-review הבא**, והוא **שומר את הכל** — score, feedback, היסטוריה, ותאריך.
>
> ושימו לב מה זה יוצר — **feedback loop**. כל תשובה שלי משנה את מה שאני אקבל מחר. המערכת לא סטטית; היא מתכווננת אליי.

# 8 · Active Recall & Spaced Repetition — 0:50

**על המסך:** שקף Spaced Repetition / SM-2.

> ומאחורי ה-loop הזה יש שתי שיטות למידה מוכחות, ורציתי שהמערכת תממש אותן באמת.

# 9 · Architecture — 1:30

**על המסך:** שקף Architecture. **לעבור לפי הקבוצות שעל המסך, לא לפי כל חץ.**

> וזו הארכיטקטורה המלאה. אני אעבור על הרכיבים המרכזיים לפי הזרימה של בקשה אחת.
>
> **Frontend** — ב-**Next.js**. ומשהו שעשיתי בכוונה: ה-Frontend מדבר עם **service אחד בלבד**. לא עם חמישה. כשמשהו לא עובד — יש מקום אחד לבדוק בו.
>
> ה-service הזה הוא ה-**backend** שלי, ה-**Tutor Agent**. הוא ה-**orchestrator** של כל המערכת: מקבל את הבקשה, מבין מה צריך לקרות, ומפעיל את מי שצריך.
>
> בתוכו — **LangGraph**, שמנהל את ה-workflow, ושני **sub-agents**: **Card Creator** ו-**Card Grader**. על החלק הזה אני ארחיב בשקף הבא, כי זה החלק הכי מעניין בפרויקט.
>
> לידם — **SM-2**, שכמו שאמרתי הוא Python ולא AI.
>
> מתחת לכל זה — שכבת ה-**MCP Server**, שכתבתי בעצמי. כל גישה למידע עוברת דרכה.
>
> ומאחורה — ה-storage. **DynamoDB** ל-decks, ל-cards, ל-history ול-learner profile: הכל לפי key, בלי joins, עם **GSI** על ה-due date כדי לשלוף את מה שהגיע זמנו בלי לעשות scan על כל הטבלה. ו-**S3** לחומרים הגולמיים, ל-logs ול-Terraform state.
>
> ומהצד — שני שירותים חיצוניים: **AWS Bedrock** בשביל ה-LLM, ו-**Deepgram** ל-speech-to-text.
>
> והכל — כל התיבות שאתם רואים כאן — רץ כ-**Docker containers** על **Kubernetes**.

# 10 · The Agent & Sub-Agent — 1:20

**על המסך:** שקף Agent / LangGraph (או zoom על החלק הזה ב-Architecture). **זה החלק שהכי חשוב — לדבר לאט ובביטחון.**

> ועכשיו החלק שהכי מעניין אותי בפרויקט — איך ה-**Agents** עובדים ביניהם.
>
> ה-**Tutor Agent** מקבל משימה — למשל "יש חומר חדש" או "יש תשובה לבדוק". והוא לא מבצע אותה בעצמו. הוא משתמש ב-**LangGraph** כדי לנהל את ה-**workflow**: LangGraph מגדיר את ה-flow כ-**graph** של nodes, עם state שעובר ביניהם, וכל node מחליט מה ה-step הבא. זה נותן לי flow צפוי, שאפשר לעקוב אחריו ולעשות לו debug — במקום prompt ענק אחד שעושה הכל.
>
> וכשצריך לייצר cards — ה-Tutor Agent פונה ל-**Sub-Agent**. ל-**Card Creator**, שכל התפקיד שלו זה לקחת חומר ולכתוב ממנו שאלות טובות. וכשצריך לבדוק תשובה — הוא פונה ל-**Card Grader**.
>
> **וזו בעצם communication between Agents** — Agent אחד מפעיל Agent אחר, מעביר לו בדיוק את מה שהוא צריך, ומקבל ממנו תוצאה מובנית בחזרה.
>
> **ולמה בכלל sub-agents?** שלוש סיבות. אחת — **התמחות**: לכל sub-agent יש prompt וכללים משלו, ולכתוב שאלה טובה זו משימה אחרת לגמרי מלדרג תשובה. שתיים — **context קטן ונקי**: כל sub-agent מקבל רק את מה שרלוונטי לו, וזה גם יותר מדויק וגם יותר זול. שלוש — **תחזוקה**: אני יכולה לשפר את ה-Grader בלי לגעת ב-Creator בכלל.
>
> ועכשיו — איך ה-Agent נוגע במידע? **דרך MCP.**
>
> ה-**MCP** הוא שכבה שנותנת ל-Agent **tools**. וזו הנקודה שהכי חשובה לי: **ה-Agent לא ניגש ל-DynamoDB ולא ל-S3 בכלל.** ה-LLM יודע לעשות reasoning — הוא לא אמור לכתוב ל-database.
>
> אז כתבתי **Study MCP Server** משלי, עם tools כמו: ליצור deck, להוסיף card, לשלוף את מה שהגיע זמנו, לשמור score, לקרוא ולעדכן profile.
>
> ה-Agent רק **מחליט** איזה tool הוא צריך — וה-**tool** הוא זה שמבצע בפועל. ככה יש הפרדה נקייה: ה-Agent לא יודע איך ה-database בנוי, והוא מקבל **interface** יציב במקום גישה ישירה.

# שאלות שסביר שיישאלו

- **למה sub-agents ולא prompt אחד?** → התמחות, context קטן יותר, ותחזוקה נפרדת.
- **למה MCP ולא פשוט לקרוא ל-database מהקוד?** → כדי שה-Agent יקבל interface של tools ולא גישה ישירה ל-storage; ה-LLM מחליט, ה-tool מבצע.
- **למה S3 וגם DynamoDB?** → S3 לקבצים גולמיים, DynamoDB ל-structured application data עם lookup לפי key.
- **מה אם ה-LLM מחזיר score לא תקין?** → נופל ל-"incorrect", וה-card חוזר מחר. ה-scheduling אף פעם לא תלוי בפורמט של ה-model.
